# PRAMAN

**Automated compliance auditing for network device configurations.**

SIH 2026 · Problem Statement **26155** · NTRO · Theme: Blockchain & Cybersecurity

Hand a router or switch configuration to PRAMAN and it returns a per-device
compliance verdict against CIS, DISA STIG, NIST SP 800-53 and ISO 27001, with
the remediation CLI the publisher wrote for each failure, signed into a
hash-chained ledger so the report can be re-checked later without trusting the
process that produced it.

It runs entirely offline on one laptop. No cloud, no API keys, no network.

---

## What it does

| PS capability | Where it lives | Status |
|---|---|---|
| **C1** Unified ingestion engine | `backend/ingest/` — pattern-driven, vendor packs are data files | 7 vendor packs shipped, 3,748 facts from 18 configs |
| **C2** AI-powered training module | `backend/ai/`, `frontend/js/views/training.js` | 3-tier classifier + GUI; new formats taught without redeploy |
| **C3** Multi-framework compliance engine | `backend/rules/` | 454 rules over 13 benchmarks → 4 frameworks, 42 catalogs / 3,366 controls |
| **C4** Actionable intelligence + PDF report | `backend/report/`, `backend/remediation/` | Per-device signed PDF, publisher-sourced fix CLI |
| **C5** Vendor-agnostic scalability | `rules/mappings/`, `data/ingest/patterns/` | A new vendor or benchmark is a YAML file, zero code changes |

The numbers above are measured, not claimed. Every one is regenerated by a
script in `scripts/` and asserted by the test suite — see
[Measured results](#measured-results) and [Verifying the claims](#verifying-the-claims).

## Setup

Requires **Python 3.10+**. Nothing else: no Docker, no Node, no database server.

```bash
cd praman && python -m venv .venv && .venv/Scripts/python.exe -m pip install -r requirements.lock.txt
```

On Linux/macOS use `.venv/bin/python` throughout instead of `.venv/Scripts/python.exe`.

Then start it:

```bash
.venv/Scripts/python.exe scripts/serve.py
```

Open <http://127.0.0.1:8012>. The UI is served by the same process as the API.

`PORT` and `HOST` are read from the environment; the default binds loopback
only. Every route except `/health`, `POST /auth/login` and the static frontend
requires an authenticated operator, but the app speaks plain HTTP — so on any
other interface the bearer token crosses the network in clear text. Put
[`deploy/nginx/praman.conf`](deploy/nginx/praman.conf) in front of it and read
[`docs/SECURITY.md`](docs/SECURITY.md) before exposing it.

### Create the first operator

There is no default account and no bootstrap endpoint, so a fresh clone has
nobody who can log in — `POST /auth/login` answers 503 and says so. Create the
first one on the machine itself:

```bash
.venv/Scripts/python.exe scripts/manage_users.py add --username you --role approver
```

Roles are ordered: `viewer` reads, `auditor` uploads and simulates, `approver`
commits audits to the ledger and teaches parser mappings. The name goes inside
the signed audit record, so choose the one an auditor should see.

### The AI tier is optional

PRAMAN runs with **no models installed**. The compliance engine is
deterministic and never depends on a model; the AI tier only helps *classify
configuration lines the pattern packs do not recognise*, and when a tier is
absent it reports its own absence rather than guessing. `tests/test_cold_start.py`
asserts this, so a fresh clone is a supported configuration rather than a
degraded one.

To enable the tiers, the download and quantisation commands are in
`MANUAL_COMMANDS.md` (available in the project workspace) — they are not run
automatically because they pull ~2.4 GB and want a GPU.

## Try it in 60 seconds

Eighteen configurations across seven vendors ship with the project, so you do
not need a device:

```bash
.venv/Scripts/python.exe scripts/fixture_report.py
```

That prints what every fixture parses to and what each framework decides about
it. To see one device control-by-control:

```bash
.venv/Scripts/python.exe scripts/fixture_report.py --detail enterprise_complex
```

Through the API, with the server running:

```bash
curl -F "file=@test_configs/realistic/telnet_exposed.conf" http://127.0.0.1:8012/ingest
```

## How it works

```
config text ──▶ pattern pack ──▶ canonical facts ──▶ rules ──▶ findings ──▶ PDF
                (YAML, per vendor)  (330 paths)      (YAML)      │            │
                      │                                          │            │
                unparsed lines                            projection    hash-chained
                      │                                    (NIST/ISO)      ledger
                      ▼                                                       │
              AI classifier tiers ──▶ Training GUI ──▶ new pattern ───────────┘
                (tfidf / setfit / LLM)   (operator confirms)   (hot-reloaded)
```

The pivot is the **canonical fact model**: every vendor's syntax is normalised
to the same 330 dotted paths, and every rule is written against those paths
rather than against a vendor's grammar. That is what makes C5 a data change —
a new vendor needs a pattern pack, not a parser; a new benchmark needs a mapping
pack, not an engine.

Read [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the two-page version —
literally two pages: [`docs/ARCHITECTURE.pdf`](docs/ARCHITECTURE.pdf) is rendered
from it by `scripts/build_architecture_pdf.py`, and the test suite both counts
its pages and re-renders it to confirm the committed PDF still says what the
Markdown says.

## Measured results

Every figure below is read from `reports/metrics/*.json`, written by
`scripts/bench/run_all.py`, and re-verified inside the test suite. Machine:
i5-13500H, 16 GB RAM, RTX 4050 Laptop (6 GB), Windows 11, Python 3.10.

**Ingestion (C1)** — 16 shipped fixtures across 7 vendors, 3,489 lines

| | |
|---|---|
| Vendor detected | 18 of 18 fixtures |
| Lines parsed | **98.49%** of 3,043 significant lines (98.83% of all 3,927) |
| Unparsed residue | 46 lines, **36 distinct commands** — enumerated in `reports/metrics/parse_coverage.json` |
| Facts extracted | 3,748 across the corpus; 430 from a single 280-line config |
| Parse latency | p50 **7.8 ms**, p95 11.5 ms (largest fixture, n=20) |

Ten of the eighteen fixtures parse at 100%, including four of the six
non-Cisco-IOS vendors outright. The largest residue is `enterprise_complex.conf`
— 18 lines, 91.4% — and it is routing configuration (BGP prefix-lists,
route-maps) that no CIS or STIG control in the loaded catalogs asks about. The
lowest rate is `crypto_ipsec_isis.conf` at 89.5%, which is four lines out of
thirty-eight. The ASA is at 99.7%: its one unparsed line is
`logging flow-export-syslogs enable`, left unmodelled on purpose because it is a
feature switch rather than a syslog destination and filing it as one inflated a
CAT I destination count — the reasoning is in the pack, on `asa_logging_host`.
PAN-OS aggregates to 99.7% across its three fixtures, and both of its unparsed
lines are deliberate: `password-complexity enabled no` has no pattern because
the control reading it fails on absence anyway, and `disable-userid-service no`
is routed to the training queue rather than the ignore list, because the `yes`
form is what the ignore list covers and the `no` form means the service is on.

| Governance reach over 16 fixtures | NIST 800-53 **43 of 1,014** (4.24%) · ISO 27001 **21 of 121** (17.36%) — projected, never evaluated directly |

| Verdicts over 16 fixtures | 1,245 decided (684 pass / 561 fail), 3,295 `notchecked`, 131 n/a, 5 `unknown` |

The 13.49% is published because it is the honest denominator: PRAMAN loads every
catalog it can crosswalk, and a control for a platform with no pattern pack
cannot be decided at all. The thirteen rows above it are what it *does* audit. Every
undecided control is returned as `notchecked` with a reason, never dropped — and
each rule pack's header names the controls it deliberately left unmapped and why,
with the cross-cutting gaps collected in [`docs/GAPS.md`](docs/GAPS.md).

**The governance row needs one more sentence, because 4.24% is the wrong shape of
number and saying so is not a hedge.** NIST and ISO are never evaluated directly —
`backend/rules/projection.py` derives them from the CIS and DISA results — so
every device gets a finding for all 1,014 current NIST controls and the
overwhelming majority are `notchecked`. Of those 1,014, **714 are enhancements**
and most of the 300 base controls are organisational: a router audit is not
failing to check `PS-03` *Personnel Screening*. A real assessment scopes SP 800-53
to a **baseline** first, and that allocation is published in SP 800-53B — a
different document from the SP 800-53 catalog this project ships against. It is
not in the repository, so no MODERATE-scoped percentage is published here and
none is estimated. [`backend/frameworks/baseline.py`](backend/frameworks/baseline.py)
implements the scoping and returns nothing until `MANUAL_COMMANDS.md` Step 16
puts the allocation on disk, at which point the scoped figure appears in
`reports/metrics/rule_latency.json` with no code change. `docs/GAPS.md` §4 records
the gap; a baseline scopes a denominator and never a verdict, so the audit path is
identical either way.

**The ATT&CK row is the one number in this table that PRAMAN authored itself, and
it is labelled that way everywhere it appears.** No publisher ships a
control → technique crosswalk for CIS or DISA network-device benchmarks — MITRE's
own mappings cover NIST 800-53 and the CIS Critical Security Controls, and a scan
of all 42 normalised catalogs for `T####` tokens returns nothing. So
[`data/frameworks/attack/canonical_map.yaml`](data/frameworks/attack/canonical_map.yaml)
asserts which canonical configuration paths imply which technique, and every
report that carries the result leads with a disclaimer saying whose judgement it
is. Everything downstream of that one assertion is the publisher's: technique
names, descriptions, URLs and the mitigations, which are read from the bundle's
own `mitigates` relationships rather than written by hand — an earlier draft did
write them by hand and five were wrong, each in the plausible direction. Only
`fail` findings are annotated, the appendix sits beside `findings` rather than
inside them so the Merkle root does not move, and the logging and accounting
families are deliberately unmapped, because a device that does not log is not
exposed to a technique — it is exposed to the technique going unnoticed. Run
`python scripts/attack_coverage.py` to print the whole join, or
`--explain snmp.community` for one path's argument.

The per-benchmark spread is the point rather than an embarrassment: coverage is
high where a configuration file decides the control and low where it does not.
PAN-OS is lowest because two-thirds of that benchmark is about content-inspection
licensing and User-ID's rights in Active Directory, neither of which appears in a
config export. Guessing at those would raise the percentage and lower the value.

**AI tier (C2)** — shipped default: tier 1 only

| | |
|---|---|
| Abstention on 42 real unparsed lines | **1.00** |
| Abstention on 10 non-config control lines | **1.00** |
| Suggestions outside the 330-path schema | 0 |
| Canonical paths tier 1 can emit at all | **15 of 330** (4.5%) |
| Escalation latency | 32 – 89 ms per line (see note) |

The latency row is the one figure here that is *not* a shipped-default number,
and it is the least stable thing this repo publishes. Tier 2 is trained on this
machine (`data/models/classifier/setfit_model`, which is gitignored and never
committed), so the run walks tier 1 → tier 2 before abstaining and pays a
sentence-transformer forward pass per line. A fresh clone stops at tier 1 and is
far faster; the abstention rows are unaffected, because both tiers declined.
`tiers_available` in `reports/metrics/ai_abstention.json` records which tiers the
run actually saw.

The range is the honest form. Four consecutive standalone runs of
`bench_llm_abstention.py` landed at 88–89 ms per line; two runs of the same
script through `scripts/bench/run_all.py` landed at 32 ms, with identical
`tiers_available` and an identical timed region (`escalate_line` over the same 42
lines, five repetitions). The model is constructed before the timer starts in
both, so this is not load cost. `TODO(verify):` the cause is not established —
until it is, quoting either end alone would be quoting a condition, not a
measurement. `latency_per_line_ms` is in `scripts/bench/__init__.py`'s `VOLATILE`
set, so `--check` does not gate on it and the suite is not flaky over this.

This is reported as *safe, not yet useful*, and the distinction matters. Tier 1
is trained on labels the deterministic parsers generated, so its label set covers
only already-parseable paths — all 15 management-plane. The unparsed residue is
routing configuration, whose correct paths are outside that set, so silence is
the best outcome available to it rather than a judgement it exercised.

It did not start there. The negative control above failed on its first run: tier
1 answered 28 of the 51 lines the population held at the time, *every one* with
the same class at ~0.93 confidence —
including for a shopping list, because a calibrated softmax over 15 imbalanced
classes reports its prior when the input carries no signal it recognises.
`"shutdown"` and `"zzzzzzzz qqqq"` both scored 0.929, which is the proof the
number was not a function of the input. The fix is an inference-time
prior-collapse guard (`backend/ai/tfidf_clf.py:PRIOR_EVIDENCE_MARGIN`) with
`tests/test_tfidf_ood_guard.py` holding it in place. The residue is closed by the
C2 training GUI — a human maps the line once and it becomes deterministic — not
by this classifier.

**On the cross-validation accuracy in `reports/metrics/classifier.json`.** That
file records the training run and reports `mean_accuracy: 0.959`. Quoted alone
it would be misleading, so: 1,581 of its 1,943 samples are one class, meaning a
constant predictor scores **0.814** on the same split. The lift over
majority-class baseline is ~14 points, not 96 points of competence, and macro-F1
is 0.858 with three classes below 0.6 and `mgmt.enable_secret.hash_type` at 0.0.
The labels were generated by running the deterministic parsers over the corpus,
so the metric measures agreement with a regex, not the ability to classify
formats the parsers never saw — which is the task C2 actually needs. It is
published because the training run happened; it is not a headline claim.

**Tiers 2 and 3 have been trained and measured on this machine.** "Shipped
default: tier 1 only" above is a statement about a *fresh clone* —
`data/models/` is gitignored, so a checkout has no tier 2 and no tier 3 — not a
statement about what exists. Both runs are recorded:

| | Tier 2 — `reports/metrics/setfit.json` | Tier 3 — `reports/metrics/qlora.json` |
|---|---|---|
| Method | SetFit few-shot over `sentence-transformers/all-MiniLM-L6-v2` | QLoRA 4-bit NF4 over `Qwen/Qwen3-4B-Instruct-2507` |
| Split | held-out **devices** (`CHIC-re0`, `LOSA-re0`, `WASH-re0`) — 1,443 train / 493 holdout, 14 classes | held-out devices — 1,864 train / 79 eval, 15 classes |
| Trained | 33.6 min | 16.4 min on the RTX 4050 Laptop (6 GB) |
| Result | accuracy **1.00**, macro-F1 **1.00** — *and see the caveat below* | train loss 0.499 → eval loss 0.249; rank 16, 11,796,480 trainable params (**0.29%** of 4.03 B) |

The 1.00 is quoted here only because it is quoted with the file's own caveat,
verbatim: *"94.1% of the 493 holdout lines are 'interface.admin_state', and 7 of
14 trained classes appear in the holdout at all. Accuracy on this split is
therefore dominated by one easy class and should not be read as a per-class
capability figure — read 'per_class' supports instead. Tier 2's real job is the
long tail, which this split barely samples."* Two of the fourteen classes fall
below the minimum support of 8 — `mgmt.enable_secret.hash_type` at 7 and
`mgmt.login_banner` at 1 — and five of the seven measured classes are decided on
three to six lines each. A perfect score over 464 `interface.admin_state` lines
and 29 of everything else is not evidence of a capable classifier; it is
evidence that the split did not test one.

Reporting it any other way would be the same failure this section already avoids
for tier 1, where the 0.959 is published beside the 0.814 a constant predictor
scores. The split is grouped **by device** rather than by line for the same
reason: two lines from the same router are near-duplicates, and splitting on
lines would put a config's own text on both sides of the boundary and measure
memorisation.

Neither tier is in the verdict path, and no tier can be. Tiers only propose a
canonical path for a line the pattern packs did not recognise; an operator
confirms it, and the confirmation becomes a deterministic pattern. The
compliance decision is made by the rule engine over facts, never by a model —
[`docs/adr/0003-ai-abstains-human-confirms.md`](docs/adr/0003-ai-abstains-human-confirms.md)
is the decision and the options it beat. Enabling either tier is a manual step,
priced in `MANUAL_COMMANDS.md`.

## Verifying the claims

A compliance tool that cannot be audited itself is not worth much, so every
published number is regenerable and every guarantee is a test.

```bash
.venv/Scripts/python.exe -m pytest -q          # 1,649 tests
.venv/Scripts/python.exe -m ruff check backend/ scripts/ tests/
.venv/Scripts/python.exe scripts/bench/run_all.py --check    # every published metric is current
.venv/Scripts/python.exe scripts/fixture_report.py --check   # published table is current
```

Four of those tests matter more than the rest:

- **`test_every_control_is_exercised_in_both_directions`** — every automated
  control passes on at least one fixture and fails on at least one. A control
  that only ever passes hides a rule that cannot detect its own violation.
- **`test_notchecked_controls_are_reported_not_dropped`** — a control PRAMAN
  cannot decide is returned as `notchecked` with a reason, never silently
  omitted. This is what stops the coverage figure from flattering the tool.
- **`test_the_published_fixture_table_is_not_stale`** — the numbers in
  `test_configs/README.md` are re-measured inside the test run, so documentation
  cannot drift away from behaviour.
- **`test_run_all_check_passes`** — re-runs every benchmark in a subprocess and
  diffs the substance against `reports/metrics/*.json`. Nothing about a stale
  number looks wrong, so this is what keeps the table above honest. Marked
  `slow`; `-m "not slow"` skips it while iterating, and it is the last thing
  that should be skipped before a submission.

**What PRAMAN does not check is written down.** [`docs/GAPS.md`](docs/GAPS.md)
lists all 19 unautomated CIS controls and 3 unautomated DISA STIG controls
individually, with the reason each one is unautomated and what it would take to
close it. The easiest way for a compliance tool to look good is to quietly not
check the hard controls; that document exists so this one cannot.

## Layout

```
backend/
  ingest/      pattern-driven parsers; a vendor is a YAML file
  canonical/   the 330-path fact vocabulary and finding model
  rules/       evaluator, conditions, framework projection
  frameworks/  catalog loading, crosswalks, control normalisation
  remediation/ resolves fix CLI from the publisher's own text (never generated)
  report/      per-device PDF, charts, signing, evidence attachment
  ledger/      hash-chained, Ed25519-signed audit records
  ai/          3-tier line classifier + the training mapping store
  threat/      MITRE ATT&CK — the bundle loader, PRAMAN's own editorial
               path → technique map, and the per-audit threat appendix
               (272 of 454 rules reach a technique; context, never a verdict)
  export/      OSCAL 1.2.3 Assessment Results and SARIF 2.1.0, both validated
               against the publishers' own JSON Schemas
  db/          SQLite connection, schema, pragmas, and an additive migration
               gated on PRAGMA user_version — a future database is refused, not
               silently written to
  app/         FastAPI routes, config, runtime state
  cli.py       offline audit without starting a server
frontend/      dependency-free ES modules, 10 views
rules/mappings/  control → condition packs (CIS, DISA STIG)
data/
  frameworks/  catalogs and crosswalks (CIS, STIG, NIST, ISO, ATT&CK)
  ingest/patterns/  vendor pattern packs
  models/      optional AI tiers (absent by default)
test_configs/  16 shipped device configurations, documented per category
docs/          architecture, gaps, security, ADRs
scripts/       every published number is produced by one of these
  bench/       run_all.py regenerates or --check-verifies reports/metrics/*.json
reports/metrics/  the measured numbers quoted in this README and the slides
tests/         1,649 tests
```
